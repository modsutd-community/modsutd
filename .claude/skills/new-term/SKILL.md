# New-term rollover

There is deliberately no term/academic-year engine in this codebase - a
human (or you) updates these spots each term. Work through all of them; a
missed one ships stale dates to students' calendars.

## 1. The academic calendar - nothing to do

`data/term-calendar.json` is generated by `tools/scraper/gather_terms.py` from
SUTD's own academic-calendar page, and the monthly `scrape` job refreshes it. It
already carries every trimester of 2026-2030, so a new term needs no edit here.

Two things depend on it, which is why it is first: a Weekly Calendar View paste
carries one week and no term, so this file is the only thing that can spread it
across the term; and `termReminders.ts` reads the teaching weeks to time the two
eval nudges, the midterm at the end of the last teaching week before recess and
the final at the end of the last one.

Check rather than edit:

```bash
cd tools/scraper && python gather_terms.py --dry-run
```

It refuses to write a thin answer, so a redesigned SUTD page fails loudly
instead of overwriting a good calendar. If it does, fix the selectors in that
file - never paste dates into the JSON.

## 2. Term label - nothing to do either

The label comes from `labelFor()` reading that same file, so it follows the
calendar. `DEFAULT_TERM_LABEL` in `frontend/src/workbench/logic.ts` is only
what to say before the fetch lands or between terms.

It does not reach `/data` in any case: `tools/fold_slots.py` prints the term and
never writes it, and room availability keys on the venue alone. A stale label is
cosmetic; it cannot corrupt a contribution.

Telegram batch chats need no step here: they key on the mod code and expire on
the term-end date a List View contribution writes into `data/term-window.json`,
so the first click of the new term opens a new batch.

## 3. Community threads

- Prune stale-term schedule slots from `data/courses/*.json` - last term's
  room occupancy is wrong the moment the new term starts. (Slots auto-commit
  on main via the timetable-contribution workflow; there is no PR to merge.)
  A slot carries no term, so nothing but the calendar date tells you which term
  it came from. Prune by the commit, not by a field.

## 4. Schedule data

- If SUTD has published the official term timetable: ingest real schedules
  into `data/courses/*.json` (see the `course-data` skill for shape rules).
  Remove the placeholder labelling **only** for mods whose schedules are now
  real.
- If not: placeholders stay, labelled as placeholders. Never dress them up
  as real.

## 5. Rotate the batch-chat link key (optional now)

`telegram-prune.yml` deletes expired entries from the registry on the first
Saturday of each month, so last term's ciphertext leaves the public repo
without anyone doing anything. That was the reason rotation was load-bearing, so forgetting this step
no longer leaves old chats exposed - it is hygiene, not a deadline.

Still worth doing when convenient, a few days AFTER the old term ends.

```bash
openssl rand -base64 32
gh secret set TG_LINK_KEY --repo modsutd-community/modsutd
vercel env add TG_LINK_KEY production
vercel env add TG_LINK_KEY preview     # then redeploy
```

Rotating deliberately makes every previous term's `linkEnc` undecryptable.
That is the point: last term's chats are obsolete, their registry entries have
expired out of the UI already, and a key that never changes is one leak away
from publishing every group modSUTD ever made.

Two side effects, both harmless. Every account's `MIN_AGE_DAYS` draw is an HMAC
under this key, so thresholds reshuffle. And any group created but not yet
expired becomes unreachable - so rotate in the gap between terms, never mid-term.

Then prune the expired entries from `data/telegram-groups.json` in the same PR;
their ciphertext is now dead weight.

## 6. Verify & ship

Run `npm run merge-ready` in `frontend/`.

Then spot-check by hand: paste a timetable on `/timetable`, export `.ics`, open it
in a calendar app - events must recur weekly across the new term's date
range, not span it as one block. PR title: `data: term rollover <term>`.

## Known coupling

- e2e specs assert on some live data values (`e2e/venues.spec.ts`); a data
  change can fail CI with no code change. Fix the spec expectation in the
  same PR, don't delete the assertion.
